# 複数人で同じ Scene / Prefab を触ったときのマージコンフリクト詳細ガイド

複数人が **同じ `.unity`（Scene）/ `.prefab`（Prefab）** に手を付けた場合に、
**何をするとマージコンフリクト（または事故）になるのか**を事細かく整理したドキュメント。
[GitWorkflow.md](GitWorkflow.md) の §7（競合の解消）と [UnityRules.md](../02_Development_Guidelines/UnityRules.md) の補足にあたる。

> ⚠️ 前提：現在このリポジトリは **Unity Smart Merge（UnityYAMLMerge）を無効化**している（`.gitattributes` の `merge=unityyamlmerge` 割り当てと `.git/config` のドライバ定義を削除済み）。
> そのため Scene / Prefab の競合は **git の通常テキストマージ**で処理され、自動解決されない＝**コンフリクトが出やすく・手動解決が必要**になる。本ガイドの重要度はこれにより上がっている。

---

## 0. 大前提：なぜ Scene / Prefab は競合しやすいのか

`.unity` と `.prefab` は中身が **YAML テキスト**だが、人間が読み書きする想定ではなく **Unity が機械生成する**フォーマット。次の特徴がコンフリクトを誘発する。

1. **1ファイルに大量のオブジェクトが詰まっている**
   1つの Scene ファイルに、全 GameObject・Transform・Component・参照が連なって入っている。誰がどこを触っても**同じファイルの近接行**を変更しがち。
2. **`fileID`（ローカルID）で相互参照している**
   オブジェクトやコンポーネントは `--- !u!1 &123456789` のような **fileID** で識別され、参照は `{fileID: 123456789}` で繋がる。新規追加時にこの巨大な数値が振られ、**同時に別々の追加をすると別ファイルで別 fileID が振られて衝突・重複**する。
3. **順序・整形の差分が出る**
   Unity はオブジェクトの並び順や `m_Children` の列挙順を内部都合で書き換えることがある。**実質同じでも行が動く**ため、テキストマージは「両方が変更した」と誤認しやすい。
4. **改行コード / エンコーディングの差**
   CRLF↔LF や BOM の有無が混ざると、**全行が差分**になり丸ごと競合する（[GitWorkflow.md](GitWorkflow.md) §4.1 のレビュー観点参照）。

---

## 1. 【高確率でコンフリクトする操作】同じ Scene を2人が編集

以下は **2人が同じ `.unity` / `.prefab` を別ブランチで編集 → 両方を main に取り込む** ときに、ほぼ確実〜高確率で競合する操作。

### 1-1. ルート階層へのオブジェクト追加（最頻）
- 2人が同じ Scene に **新規 GameObject を追加**すると、Scene 末尾付近に互いの定義が追記され、**同じ行範囲＋ Scene Roots のリスト（`m_Roots` / SceneRoots の `m_Children`）**で競合する。
- さらに両者で **同じ fileID が偶然振られる**と、マージ後に**ID 重複でシーンが壊れる**（テキスト的には解決できても Unity が読めない）。

### 1-2. Hierarchy の並び替え・親子付け替え
- オブジェクトを**ドラッグで並び替え／別の親へ移動**すると `m_Father` `m_Children` `m_RootOrder` が書き換わる。
- 2人がそれぞれ別の並び替えをすると、**Transform の子リストが両側で変化**して競合。テキストマージで適当に繋ぐと**親子関係が壊れる/ループする**。
- 今回の「オブジェクトをまとめた（空オブジェクト配下に再ペアレント）」操作は **まさにこの 1-2 に該当**し、他者が同じ Scene の階層を触っていると競合・破損しやすい。

### 1-3. 同一オブジェクト/コンポーネントの値編集
- 2人が**同じ Transform の position/rotation/scale** や **同じ Component のフィールド**を変えると、その数行で競合。
- 1人が**コンポーネントを削除**、もう1人が**そのコンポーネントの値を編集**すると、削除側 vs 変更側で競合（解決を誤ると参照だけ残って `Missing` になる）。

### 1-4. ライト/レンダリング/環境設定の変更
- **Lighting 設定**（環境光・Fog・Skybox）、**Light コンポーネントの追加/設定**、Scene 内の **Volume / Post-process** などは Scene ファイル先頭〜各所に散らばって書かれ、複数人が触ると競合。
- ライトをベイクすると **Lighting Data Asset（`*.lighting` / ライトマップ）** も変わり、これも競合源。

### 1-5. Prefab インスタンスのオーバーライド競合
- Scene 上に置いた **Prefab インスタンスのプロパティを上書き（override）**すると `m_Modifications` に差分行が増える。
- 2人が同じインスタンスを別々に override すると `m_Modifications` で競合。
- 片方が **Prefab 本体（`.prefab`）を変更**、もう片方が**そのインスタンスを override** すると、Scene と Prefab の両ファイルで整合が崩れる。

### 1-6. Prefab 本体（`.prefab`）の同時編集
- Scene と同じ理由で `.prefab` も競合する。特に **Prefab Variant / ネストした Prefab** は参照（`m_SourcePrefab` / fileID）が複雑で、競合解決ミスが波及しやすい。

## 2. 【コンフリクトしにくい / 比較的安全な操作】

- **別々の Scene** を各自が編集する（最も安全。担当 Scene を分ける）。
- **新規 Prefab / 新規アセットを追加するだけ**（既存 Scene を触らない）。新規ファイルは衝突しない。ただし `.meta`（GUID）が重複しないよう、**同じアセットを2人がそれぞれ別途インポートしない**こと。
- スクリプト（`.cs`）の編集は通常のテキストマージが効くため、Scene よりは扱いやすい（それでも同一行は競合する）。

> 注意：「安全」とはあくまで *相対的* な話。同じ Scene を触る以上、ゼロにはできない。

---

## 3. コンフリクト・事故を防ぐ運用ルール

1. **1 Scene は同時に1人**を原則にする。やむを得ず複数人で触る場合は、**事前に編集範囲（どのオブジェクト群か）を共有**する（[UnityRules.md](../02_Development_Guidelines/UnityRules.md) §2）。
2. **大きな Scene 変更は小分けに**して、こまめにブランチを main へ取り込む。長期間ブランチを寝かせない（差分が育つほど競合は深刻化）。
3. **無関係な差分を混ぜない。** まとめ作業・並び替えだけのコミットに、ついでの位置調整や Inspector 差分を入れない。
4. **作業前に `main` を取り込む。** 自分のブランチで作業を始める前・main へ戻す前に最新 main を取り込み、競合を早期に小さく解消する。
5. **git 操作の前に必ず Unity で保存（Ctrl+S）。** 未保存はディスク＝git から不可視。未保存のまま checkout/merge/pull すると**メモリ上の作業が消える**（[GitWorkflow.md](GitWorkflow.md) §6.5 に実際の事故記録あり）。**これはコンフリクトとは別系統の事故**だが、同じ Scene 作業で最も多い消失原因。
6. **再ペアレント（オブジェクトのまとめ）や大規模な並び替えを行うブランチは、最優先で main に合流**させ、他者の同 Scene 作業より先に取り込む。後出しほど競合解決が困難。
7. 改行コードを統一する（`.gitattributes` 参照）。CRLF↔LF だけの全行差分を出さない。

## 4. それでもコンフリクトが起きたときの対処

1. **慌てて手で YAML を繋がない。** Scene / Prefab のテキストを手動でマージするのは破損リスクが非常に高い。
2. **まず Unity を閉じる前にシーンを保存**し、コンフリクト中のファイルを別名でバックアップする。
3. 原則は **「どちらかのバージョンを丸ごと採用」** が安全：
   ```bash
   # 自分の変更を全採用（相手の同ファイル変更は捨てる）
   git checkout --ours  "Assets/Scenes/MainScene.unity"
   # 相手の変更を全採用（自分の同ファイル変更は捨てる）
   git checkout --theirs "Assets/Scenes/MainScene.unity"
   git add "Assets/Scenes/MainScene.unity"
   ```
   捨てた側の変更は **Unity 上で手作業で再適用**する（テキストで混ぜるより安全で確実）。
4. どうしても両者の変更を活かしたい場合は、**片方を採用 → Unity で開いて、もう片方の変更内容を画面上で再現**する。
5. 解決後は **必ず Unity で Scene を開いて壊れていないか確認**（Missing 参照・重複・階層崩れ）。テキスト上 OK でも Unity が読めない／壊れているケースがある。
6. 万一未保存作業が消えた場合は、`Temp/__Backupscenes/*.backup`（Unity 自動バックアップ）を退避してから復旧を試みる。

## 5. Smart Merge（UnityYAMLMerge）の扱いについて（要確認事項）

- 本リポジトリでは現在 Smart Merge を**無効化**している。
- 一方 [GitWorkflow.md](GitWorkflow.md) §6.5.1 には「SmartMerge は有益なツールであり**削除してはならない**」と明記されており、**この2つは矛盾している**。
- Smart Merge は本来、Scene / Prefab の競合を **fileID 単位で意味的にマージ**して自動解決を助けるツールで、上記 §1 の競合の多くを軽減できる。
- 「リモート側が一方的に残る」現象は、**ドライバ設定（`--force` / `--fallback` / 引数順）の問題**である可能性があり、削除ではなく**設定の修正で直る**ことがある。
- → 運用方針を確定させ、**「無効化を維持して本ドキュメントを正とする」か「Smart Merge を正しく設定し直して GitWorkflow.md に揃える」かを決める**こと。決定後、矛盾しているドキュメント側を更新する。
